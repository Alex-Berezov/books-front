# /qa - проверка сделанного до сдачи

Порядок жёсткий. Шаг нельзя пропустить и нельзя поменять местами с соседним.

## 1. Собрать дифф

```
git rev-parse --abbrev-ref HEAD
git merge-base HEAD main
git diff --merge-base main --name-status
git diff --merge-base main --stat
git status --porcelain
```

Считай диффом и незакоммиченные правки, и новые неотслеживаемые файлы.

Дифф пуст - напиши одной строкой «Изменений против main нет, проверять нечего» и выйди.
Ничего больше не запускай: ни ревьюеров, ни гейты.

## 2. Четыре ревьюера, все сразу

Вызови четырёх подагентов **одним сообщением, четырьмя вызовами Task подряд** - тогда они пойдут
параллельно. По одному, дожидаясь ответа, запускать нельзя: это вчетверо дольше и без пользы.

Имена смотри в `.claude/agents/`. В `books` они с префиксом: `books-correctness`, `books-data`,
`books-conventions`, `books-tests`. В `books-front` без префикса: `correctness`, `data`,
`conventions`, `tests`.

Каждому передай одинаковый пакет:

- ветку и точку отсчёта (вывод `git merge-base HEAD main`);
- полный список изменённых файлов с признаком A/M/D;
- сам дифф `git diff --merge-base main` (велик - передай `--stat` и список файлов, а полный дифф
  ревьюер добирает сам указанными в его инструкции командами);
- одну строку о том, что требовалось сделать - постановку задачи, а не то, как ты её решал.

Чего в задании ревьюеру быть не должно:

- твоих объяснений, почему код написан именно так - ревьюер с ними согласится, и смысл ревью пропадёт;
- твоей оценки серьёзности находок и списка мест, «которые точно в порядке»;
- просьбы «проверь только вот это» - зона ревьюера описана в его файле, сужать её ты не вправе.

Ревьюеры обязаны идти в свежем контексте: они не видели, как ты работал, и не должны узнать этого
от тебя. Твоё дело - дать дифф и постановку.

Отчёт «нарушений не нашёл» принимается только вместе с разбором чек-листа: какие пункты
неприменимы и почему. Пришёл пустой отчёт без разбора - это брак, верни ревьюера с формулировкой
«пройди чек-лист по пунктам» и дождись нормального ответа.

## 3. Встроенное code-review

Дополнительно запусти встроенную команду:

```
/code-review high
```

Её находки идут в общую таблицу наравне с находками подагентов, источник - `code-review`.

## 4. Свести всё в одну таблицу

Одна таблица на весь прогон, строки от блокеров к придиркам:

| Серьёзность | Файл:строка | Что не так | Правило | Что сломается | Кто нашёл |
| ----------- | ----------- | ---------- | ------- | ------------- | --------- |

- Серьёзность: `блокер`, `замечание`, `придирка`.
- Одна и та же находка от разных ревьюеров - одна строка, в «Кто нашёл» перечисли всех через запятую.
  Совпадение по файлу и сути, а не по формулировке.
- Расходятся в серьёзности - бери высшую.
- Формулировку не смягчай и не переписывай в свою пользу. Не согласен с находкой - оставь строку
  в таблице и допиши возражение отдельной строкой под ней, а не вместо неё.
- Находка без правила из `rules.json`, `qa-lessons.md`, `STYLE_GUIDE.md`, `AGENTS.md`, ADR или
  LEGACY в таблицу не идёт.

## 5. Гейты

```
node .claude/hooks/gates.js
```

Приведи фактический вывод команды: сами строки и код возврата. Пересказ словами вместо вывода
не принимается ни при каком результате.

## 6. Обнулить счётчик правок

Ровно эта команда, из корня репозитория:

```
node -e "const fs=require('fs'),p='.claude/.qa-state';let s={};try{s=JSON.parse(fs.readFileSync(p,'utf8'))}catch(e){}s.edits=0;s.strayFiles=[];s.lastQa=new Date().toISOString();fs.writeFileSync(p,JSON.stringify(s,null,2));console.log(JSON.stringify(s))"
```

Она ставит `edits` в ноль, очищает `strayFiles` и пишет дату прогона в `lastQa`. Запускать её
можно только после шагов 2-5, а не заранее и не вместо них.

## 7. Итог

Есть блокеры - перечисли их списком и остановись. Правки по ним в этом же ходу не начинай:
человек должен увидеть список раньше, чем ты начнёшь его разбирать.

Блокеров нет - одной строкой скажи это и назови, сколько осталось замечаний и придирок.
